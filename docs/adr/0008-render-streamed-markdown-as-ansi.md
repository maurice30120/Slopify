# Rendre le Markdown streamé de l'agent en ANSI dans le terminal

Le mode `--verbose` de `slopify run` stream en direct le contenu des `agent_thought_chunk` et `agent_message_chunk` via `writeErrorRaw`. Le Markdown produit par l'agent (titres, gras, listes, blocs de code) arrive tel quel, illisible dans un terminal. Nous intégrons `markstream-cli` pour rendre ce Markdown en ANSI pendant le streaming, uniquement quand le flux d'erreur est un TTY. Sur un flux non-TTY (pipe, CI, tests) ou avec `SLOPIFY_ANSI_STREAM=0`, le texte brut est écrit inchangé pour préserver les consumers existants.

Le rendu se fait **par blocs terminés**, pas par patches de curseur. Un tampon Markdown propre est tenu par exécution, nœud et phase (pensée/réponse). À chaque chunk, on accumule le texte, puis on identifie avec le parseur Markdown de la dépendance existante (`markdown-it` via `markstream-cli`) la ligne de départ du dernier bloc de haut niveau. Tout ce qui précède cette ligne est « stabilisé » et rendu une seule fois par `highlightMarkdown`, puis ajouté à stderr **sans effacer ni réécrire** le contenu précédent. Le dernier bloc de haut niveau est conservé tant qu'il peut encore grandir — notamment les listes, tableaux, blocs de code et le paragraphe en cours — jusqu'à l'arrivée du bloc suivant ou au vidage final. Le tampon restant est vidé à la transition pensée/réponse, à la fin du nœud et avant toute sortie de fin ou d'erreur ; son état est ensuite libéré.

Ce choix conserve la mise en forme dans le terminal intégré tout en évitant les répétitions : le renderer à déplacements de curseur (`createMarkdownStreamRenderer`, patches ANSI avec save/restore/erase) réécrivait le même contenu à chaque chunk — un essai local montrait 16 écritures du même titre pour 21 chunks — et les terminaux intégrés qui n'interprètent pas ces patches affichaient les copies. Le rendu par blocs écrit chaque bloc exactement une fois ; seules les couleurs ANSI (SGR) sont produites, aucune commande de déplacement ou d'effacement du curseur. Les séquences de contrôle terminal venant du texte de l'agent restent sanitized par défaut (`allowControlSequences: false`).

`markstream-cli` reste déclarée comme dépendance de `slopify/package.json`. Le workspace hoiste le paquet pendant le développement, tandis que le bundle esbuild l'embarque dans la CLI publiée. La détection des deltas par rapport aux snapshots cumulatifs (certains adaptateurs ACP renvoient le texte cumulatif plutôt que le delta) est inchangée et non élargie : le tampon par blocs reçoit le delta déjà calculé.

**Considered Options:**
- *Renderer à déplacements de curseur (`createMarkdownStreamRenderer`)* : retenu initialement pour son mode `smart` et la sanitization, puis remplacé. Il produit des patches ANSI (delta avec cursor save/restore/erase) qui réécrivent le contenu à chaque chunk ; les terminaux intégrés qui ne gèrent pas ces patches répètent les blocs. Le rendu par blocs écrit une seule fois sans déplacement de curseur, ce qui résout le défaut observé.
- *`markdansi`* : rejeté. Markdown→ANSI avec streaming, plus léger, mais moins mature (v0.x) et l'API de streaming append-only est moins documentée.
- *`marked` + `marked-terminal`* : rejeté. Établi (~1500 dépendants) mais pensé comme un renderer Markdown→terminal classique, pas pour le streaming incomplet. Ne gère pas nativement un bloc ` ```ts ` ouvert ou une liste en cours.
- *Texte brut inchangé* : rejeté. Le Markdown brut est illisible dans un terminal (syntaxe `#`, `**`, ` ``` ` visible) et nuit à l'expérience verbose.
- *Shiki (highlighting des blocs de code)* : différée. `markstream-cli` supporte `createShikiHighlightCode` mais l'option `highlightCode` est asynchrone (`flush()` retourne `Promise<string[]>`). Les callbacks `onSessionUpdate` / `onEvent` du runtime sont synchrones ; intégrer l'async nécessiterait de repenser le cycle de vie du renderer. Le highlighting sera ajouté si le besoin se confirme.

**Consequences:**
- `CliTerminal` expose deux membres en lecture seule : `supportsAnsi` (bool, `errorStream.isTTY`) et `columns` (nombre, `errorStream.columns ?? 80`). Les mocks `FakeTerminal` des tests implémentent ces membres (`supportsAnsi = false` par défaut).
- Sur TTY, le rendu par blocs est le comportement par défaut. `SLOPIFY_ANSI_STREAM=0` le désactive et retombe sur le texte brut, comme sur un flux non-TTY. Aucun changement d'API publique.
- Le bundle `dist/bin/cli.js` embarque `markstream-cli` (esbuild). Shiki est tree-shaken (1 référence résiduelle = un chemin en commentaire).
- `markstream-cli` exige Node 22+ ; le repo exige déjà Node 22.19+ (`engines`), donc compatible.
- La sanitization par défaut (`allowControlSequences: false`) neutralise les séquences ESC/BEL du texte LLM : elles sont rendues visibles au lieu d'être exécutées. Si un cas légitime nécessite des séquences de contrôle, il faudra activer `allowControlSequences` explicitement.
- L'affichage est fluidifié par blocs : aucun affichage caractère par caractère n'est garanti. Les blocs terminés apparaissent au fil de l'eau ; le dernier bloc en cours n'apparaît qu'à la fermeture ou au vidage. La validation dans le terminal intégré concerné reste nécessaire pour confirmer la résolution complète.
