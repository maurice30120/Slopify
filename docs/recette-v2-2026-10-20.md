PR d'intégration : [#170](https://github.com/maurice30120/Slopify/pull/170).

## Objet et méthode

Recette de la V2 refondue, incluant les PR empilées #152, #154, #164–#169
et les dernières corrections de la PR #170. Chaque run conserve sa branche Git
d'intégration, son commit de base, ses tentatives, clones privés, checkpoints,
bundles, journaux et états durables ; le workspace utilisateur est inchangé.

La preuve automatisée repose sur `.github/workflows/ci.yml` :

1. Ubuntu et macOS avec Node 22 ; `npm ci`.
2. `npm run clean`, `npm run build`, `npm test`. Tests utilisant de vrais repos Git temporaires, de faux exécutables/transport `sbx` et de faux agents.
3. `npm run audit:v2` — dix workspaces, exports publics, aucun cycle de dépendances de production, pas d'import source privé, pas de dépendance d'exécuteur concret dans `@slopify/task-batches`.
4. Installer `scripts/install.sh` dans un répertoire `bin` temporaire, invoquer la CLI via son symlink, puis `slopify init --host all --yes --json` avec `npx` **simulé**, et vérifier les templates Pi/Codex.
5. `npm pack --dry-run -w slopify` : vérification des métadonnées de l'archive CLI.

**Les smokes réels restent exclus de la CI**, y compris sur macOS :
`npm run smoke:local` utilise les comptes et configurations Pi/Codex du Mac personnel ;
`npm run smoke:docker` nécessite Docker Sandboxes sur ce même poste.
Ne pas déclarer ces vérifications passées tant que le développeur ne les a pas
exécutées et fourni les preuves retenues. `npm pack --dry-run` ne démontre pas
à lui seul l'installation de l'archive publiée hors du monorepo.

## Décision de livraison

La recette automatisée est **un prérequis de revue**, pas une autorisation de
fusion automatique. Elle est acceptée uniquement après une **CI complète
verte sur les deux OS** pour le SHA final. La validation fonctionnelle totale
de #138 et #155 reste conditionnée aux deux smokes manuels sur le Mac du
développeur et à l'inspection de leurs preuves (agents réels Pi et Codex,
checkpoint, revue, intégration, aucune mutation du workspace).

La PR #170 et les PR parentes doivent être intégrées dans l'ordre de leurs
bases ; aucune modification directe de `main` ni suppression automatique de
branches n'est demandée. Éviter de lancer deux `npm test` simultanément ou
des smokes réels depuis Actions ; en cas de saturation de processus, arrêter
immédiatement toute relance.
