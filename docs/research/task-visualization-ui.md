# Visualiser les tâches d’un run Slopify

Recherche pour le ticket [Évaluer les surfaces et technologies UI pour visualiser les runs](https://github.com/maurice30120/Slopify/issues/95), vérifiée le 17 octobre 2026. Cette note compare les surfaces et les bibliothèques possibles ; elle ne choisit pas une implémentation.

## État du contrat dans le dépôt

La branche inspectée contient le package CLI `slopify` version `0.1.0`, configuré comme binaire ESM `slopify` et exigeant Node `>=22.19.0`. Les commandes exposées sont `list`, `run` et `resume`, avec `--cwd`, `--json` et `--verbose`. Le package inclut actuellement `dist/src` seulement ; une interface web compilée devrait donc être ajoutée explicitement au paquet. Il n’y a pas de framework UI déclaré dans les dépendances du package (`slopify/package.json`, `slopify/src/args.ts`, `slopify/README.md`).

Le runtime actuel est Pipeline v3 : les nœuds portent leurs dépendances (`needs`), leurs tentatives et leurs sorties ; un plan d’exécution dynamique peut être ajouté au run. Les instantanés se trouvent sous `.acp/runs-v3/workspace/runs/<runId>/snapshot.json`, avec un `events.ndjson` append-only. Un snapshot expose notamment l’état du run, les états et horodatages des nœuds, les tentatives, les diagnostics, les artefacts, la limite de concurrence et, le cas échéant, le plan dynamique et l’état d’intégration des sandboxes (`acp-pipeline/src/PipelineRunStore.ts`, `acp-pipeline/src/PipelineV3Types.ts`, `acp-pipeline/src/ExecutionPlan.ts`).

Ces fichiers ne constituent pas encore une API de lecture complète. `FilePipelineRunStore` sait charger un run par identifiant et lister les runs récupérables, mais ne fournit pas de méthode de liste historique ni de lecture des événements ; `readEvents` n’existe que dans le store en mémoire. Le `--json` CLI retourne le catalogue de pipelines ou le résultat final simplifié, sans snapshot ni flux d’événements (`slopify/src/run.ts`, `acp-pipeline/src/PipelineRunStore.ts`). Une interface qui parcourt les anciens runs devrait donc ajouter un service de lecture stable plutôt que dépendre directement de détails internes du répertoire.

Il existe deux flux d’événements distincts. `events.ndjson` conserve les transitions du runtime, mais `PipelineRuntime` n’y ajoute pas les événements `agent_activity`. La CLI écrit les événements hôte et les mises à jour ACP en JSONL sous `.acp/logs`; elle efface ce répertoire au début de chaque nouveau run. Les chunks de message d’agent peuvent y être enregistrés en clair, tandis que le texte de pensée est remplacé par son nombre d’octets (`acp-pipeline/src/PipelineRuntime.ts`, `slopify/src/host.ts`). Lors d’une reprise depuis un nouveau processus CLI, le writer du journal du run précédent n’est pas réattaché ; ce flux n’est donc pas une archive d’activité complète et durable.

Le snapshot ne fige pas le graphe statique compilé : il conserve le `pipelineId`, puis la reprise retrouve le programme dans le catalogue chargé du workspace (`slopify/src/host.ts`, `acp-pipeline/src/PipelineV3Types.ts`). **Conséquence déduite du code :** si la définition d’un pipeline change, une vue historique ne doit pas présenter silencieusement le graphe actuel comme s’il était celui du run passé. Il faudrait conserver une version ou empreinte de la définition, ou copier le graphe compilé dans le snapshot.

## Mesures utiles et disponibilité des données

| Mesure affichée | Source ou calcul | Limite actuelle |
|---|---|---|
| Statut du run et tâches terminées, actives, en pause, échouées ou annulées | `snapshot.status` et `snapshot.nodeStates` | Donnée directe. Afficher les comptes et le total avant un pourcentage : le plan dynamique peut ne pas être étendu, et `pending` mélange attente de dépendances et attente de capacité. |
| Cause d’attente et graphe des dépendances | `needs` du programme ou `executionPlan.plan.nodes`, croisé avec les états | Le graphe est connu, mais la raison « attend une dépendance » est calculée par l’interface. Une tâche `pending` dont les dépendances sont achevées peut être en file si la concurrence est limitée. |
| Durée du run et durée bout-à-bout d’un nœud | Horodatages du snapshot et événements de début/fin | Calculable. `startedAt` d’un nœud est conservé depuis son premier démarrage ; sa durée inclut donc reprises et backoffs, elle ne sépare pas les tentatives. Les pauses doivent être distinguées si l’on veut une durée d’exécution active. |
| Concurrence et vagues | Événements `node_started` / `node_completed`, croisés avec `maxConcurrency` | Historique dérivable du flux runtime ; les événements n’incluent pas le numéro de tentative. Les reprises après interruption rendent la chronologie moins précise. |
| Tentatives, erreurs et conflits d’intégration | Compteur `attempts`, diagnostics, `sandboxRuns.integrationState`, checkpoints et fichiers | Les compteurs et états finaux sont directs ; la durée par tentative n’est pas enregistrée. Les checkpoints peuvent exposer le nombre de fichiers et le diff. |
| Dernière activité d’un agent | Mises à jour ACP présentes dans `.acp/logs` | Seulement pour le journal conservé du run courant, avec du contenu de message potentiellement sensible. Ne pas assimiler volume de texte ou pensée à qualité ou productivité. |
| Coût, tokens, appels d’outils et ETA fiable | Aucun compteur normalisé dans le snapshot ou les événements runtime | À instrumenter séparément. `promptBytes` et `textBytes` enregistrent des tailles en octets, pas des tokens ni un coût ; les mises à jour ACP brutes ne constituent pas un compteur stable. Une ETA demanderait des données historiques comparables et une définition explicite. |

Un premier tableau de bord pourrait donc montrer les faits directement disponibles (états, compteurs, durée bout-à-bout, tentatives, intégration), puis marquer visuellement les calculs dérivés. Une barre « 73 % » donnerait une précision trompeuse avant de fixer le comportement du dénominateur pour les plans non étendus, les pauses et les échecs ; `12/18 tâches terminées · 2 actives · 4 en attente` reste interprétable.

## Surfaces possibles

| Surface | Invocation et distribution dans Slopify | Atouts pour cette vue | Coûts et limites |
|---|---|---|---|
| **Interface web locale** | Commande possible `slopify ui --cwd …` : le processus Node sert les assets compilés et une API de lecture locale, puis ouvre le navigateur. Vite produit des assets statiques de production ; son serveur `preview` est documenté pour la prévisualisation, pas pour servir la production. Node fournit le module HTTP du processus déjà requis par le CLI ([Vite — build de production](https://vite.dev/guide/build.html), [Node.js — HTTP](https://nodejs.org/api/http.html)). | Grand espace de canvas, zoom, sélection, panneau de détail et axe temporel ; pas d’installeur séparé. La même interface web peut être réutilisée ultérieurement dans un conteneur desktop. | Ajoute une frontière HTTP locale et un contrat JSON/événements ; le processus doit gérer l’accès au bon workspace, l’arrêt et l’authenticité des données. Le paquet NPM doit embarquer les assets. Navigation et API locales restent à concevoir. |
| **TUI intégrée à la CLI** | Commande ou mode interactif `slopify monitor`; même installation Node/NPM et même accès direct au runtime. La CLI utilise déjà `node:readline/promises` pour ses interactions. Pour des composants réactifs, Ink apporte un rendu React en Flexbox dans le terminal ([Node.js — readline/promises](https://nodejs.org/api/readline.html), [Ink — documentation du projet](https://github.com/vadimdemedes/ink)). | Chemin de distribution et d’invocation le plus proche de l’existant ; pratique pour suivre un run depuis le terminal, avec filtres, liste, état, compteurs et graphe ASCII. | La largeur/hauteur du terminal limite les labels et l’exploration simultanée du DAG et de la chronologie. Ink ajoute React et une dépendance de rendu ; sa détection TTY et ses modes interactifs doivent cohabiter avec `--json`, CI et les sorties pipées (documentés dans le README d’Ink). |
| **Application desktop** | Installateur par plateforme ; ouvre directement le workspace et peut garder un tableau de bord accessible hors du terminal. Tauri accepte des interfaces HTML/CSS/JS et s’appuie sur la webview système ; Electron embarque Chromium et Node. ([Tauri — présentation](https://v2.tauri.app/start/), [Electron — modèle de processus](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron — pourquoi](https://www.electronjs.org/docs/latest/why-electron)). | Fenêtre persistante, accès possible aux intégrations natives (par exemple les notifications système Tauri) et réutilisation de l’UI web ([Tauri — notifications](https://v2.tauri.app/plugin/notification/)). | Nouveau produit de distribution : builds, signatures et canaux de distribution par OS. Avec Tauri, réutiliser Slopify sans demander Node installé implique de fournir un binaire sidecar pour chaque cible ; la documentation demande des binaires suffixés par target triple et une permission d’exécution. Electron réutilise plus naturellement les modules Node dans le processus principal, mais distribue également Chromium et Node avec l’app et impose une séparation main/renderer. ([Tauri — sidecars](https://v2.tauri.app/develop/sidecar/), [Tauri — distribution](https://v2.tauri.app/distribute/), [Electron — distribution](https://www.electronjs.org/docs/latest/tutorial/distribution-overview)). |

La TUI convient à une observation rapide et aux environnements sans navigateur. Le navigateur local convient à l’exploration spatiale d’un run. Desktop devient pertinent si l’usage exige une application installée, une présence persistante ou une expérience sans environnement Node ; il ajoute le plus de décisions de distribution. Ces correspondances sont des inférences à partir des contraintes de données et des capacités documentées, pas un choix de surface.

## Bibliothèques TypeScript pour les vues

### Graphe de dépendances

| Option | Ce qu’elle apporte | Compromis pour un graphe Slopify |
|---|---|---|
| **React Flow (`@xyflow/react`)** | Composant React pour des nœuds et arêtes interactifs ; zoom, pan, sélection et nœuds personnalisés intégrés. La documentation inclut des types TypeScript ([React Flow — concepts](https://reactflow.dev/learn/concepts/building-a-flow), [TypeScript](https://reactflow.dev/learn/advanced-use/typescript)). | Adapté à un graphe centré sur la tâche, cliquable, avec badge de statut et détails dans le nœud. La bibliothèque ne calcule pas elle-même la disposition : sa documentation renvoie à Dagre, ELK ou D3 ; Dagre est plus simple, ELK plus configurable et complexe ([React Flow — layout](https://reactflow.dev/learn/layouting/layouting)). |
| **Cytoscape.js** | Bibliothèque de graphe orienté données, sérialisable en JSON, avec filtres, gestes d’interaction et algorithmes de graphe ; fonctionne dans les navigateurs et aussi sans rendu dans Node ([documentation Cytoscape.js](https://js.cytoscape.org/)). | Pertinente si les requêtes, le filtrage ou les calculs de graphe deviennent centraux. Elle apporte une API de graphe complète mais moins directement intégrée au modèle React que React Flow ; l’intégration UI et le style des nœuds demandent une comparaison concrète. |

Le modèle d’exécution est un DAG de tâches, pas nécessairement un éditeur de pipeline. Les interactions qui changeraient le graphe doivent donc être désactivées ou traitées comme simples déplacements de vue dans un explorateur en lecture seule. C’est une contrainte de produit déduite du contrat existant, pas une limite de ces bibliothèques.

### Chronologie

**vis-timeline** fournit des items ponctuels ou des intervalles, des groupes (par exemple une ligne par agent), ainsi que déplacement et zoom. Le paquet NPM actuel expose des déclarations TypeScript et son dépôt publie les versions 8.5.x en 2026 ([documentation des items/groupes](https://visjs.github.io/vis/docs/timeline/), [paquet vis-timeline](https://www.npmjs.com/package/vis-timeline), [releases officielles](https://github.com/visjs/vis-timeline/releases)). Il convient à une chronologie déjà interactive, avec une intégration React à envelopper autour de son instance impérative.

Une chronologie SVG/HTML construite avec React (ou les primitives D3) fournit davantage de contrôle sur les couloirs, les pauses, les tentatives et les marqueurs d’intégration ; D3 fournit notamment les échelles temporelles, axes et comportements de zoom, mais l’assemblage et le rendu de l’interface restent à la charge de l’application ([D3 — échelles de temps](https://d3js.org/d3-scale/time), [D3 — zoom](https://d3js.org/d3-zoom), [D3 — axes](https://d3js.org/d3-axis)). React Flow et vis-timeline sont donc des spécialisations complémentaires plutôt qu’un seul composant couvrant les deux vues.

## Seams à examiner avant une décision d’implémentation

1. Définir un service de lecture commun, indépendant de la surface : `listRuns`, `getRunSnapshot`, `readRunEvents`, et `readActivity` si l’activité live est retenue. Il peut commencer en lecture seule et s’appuyer sur les fichiers existants ; le contrat actuel ne fournit pas encore toutes ces opérations.
2. Séparer données historiques et signal live. Les snapshots/événements de runtime sont durables ; `.acp/logs` est effacé au prochain run et peut contenir du texte de réponse. Définir rétention, contenu affiché et provenance de chaque événement avant d’en faire une source d’historique.
3. Figer la topologie/version du pipeline pour qu’un ancien run reste explicable après modification du workspace.
4. Décider si l’objectif est le suivi opérationnel d’un run (état, tâche bloquante, dernière activité) ou l’analyse entre runs (durées, taux d’échec, parallélisme). Le second exige une véritable indexation historique des snapshots terminaux.
5. Ajouter un numéro d’essai aux transitions, si la frise doit montrer les tentatives et calculer leurs durées indépendamment. Ajouter les données de coût/tokens uniquement si un usage de mesure a été défini et si le runtime/agent expose ces données.
