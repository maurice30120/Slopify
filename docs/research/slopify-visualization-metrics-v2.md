# Mesures disponibles pour visualiser les TaskBatch Slopify V2

Date : 17 octobre 2026. Périmètre : branche `feature/parametrage-agent`, commit `fc8eb6143342bad2c5d4c0c04f16c14d00693fda`. Cette note décrit le modèle V2 `TaskBatch` et ses sources actuelles. Elle ne reprend pas l’audit ACP v3 effectué sur une autre branche.

## Faits observés dans le code

Le snapshot durable contient l’état du run, les tâches, leurs tentatives, commits, diagnostics, éventuel conflit et contexte figé. Il est écrit sous `<store>/<runId>/state.json`; le store par défaut est dans `~/.local/share/slopify/task-runs/<hash-du-dépôt>/`. Les dates `createdAt` et `updatedAt` sont au niveau du run. [Modèle, création et sauvegarde](../../slopify/src/taskBatch.ts#L50-L102) · [Initialisation et store](../../slopify/src/taskBatch.ts#L143-L219)

Le scheduler prend, dans l’ordre JSON, jusqu’à dix tâches `pending` dont toutes les dépendances sont `succeeded`, les exécute en parallèle, puis intègre séquentiellement les tâches `completed` dans le même ordre. Il ajoute une tâche `final-review` qui dépend de toutes les tâches du lot. [Ordonnancement](../../slopify/src/taskBatch.ts#L221-L289) · [Tâche de revue finale](../../slopify/src/taskBatch.ts#L939-L963)

Le rapport calcule les huit compteurs d’état, les tâches prêtes, les tâches actives, les dépendances encore attendues et les tâches `completed` qui attendent l’intégration. Dans ce modèle, `completed` signifie « checkpoint prêt » ; `succeeded` signifie que l’intégration a abouti. Le champ nommé `progress` est un agrégat d’états et de listes, et le texte CLI affiche des compteurs : aucun n’est un pourcentage. Le rapport est une vue en lecture seule ; `running` désigne un état enregistré, pas une vérification de processus vivant. [Rapport calculé](../../slopify/src/taskBatchReport.ts#L17-L35) · [Texte de statut](../../slopify/src/taskBatchReport.ts#L133-L150)

Les tentatives sont conservées dans `task.attempts`, avec identifiant, base Git, état, code de sortie, checkpoint, chemins de rapports/logs et ressource de sandbox. Une reprise explicite par tâche (`resume-task`) produit une nouvelle tentative ; la reprise globale (`resume`) peut réutiliser un checkpoint réussi déjà présent. Le rapport de tâches expose surtout la dernière tentative ; l’historique reste dans le snapshot. [Création et résultat d’une tentative](../../slopify/src/taskBatch.ts#L402-L433) · [Reprise et nouvelle tentative](../../slopify/src/taskBatch.ts#L572-L661) · [Détails affichés](../../slopify/src/taskBatchReport.ts#L117-L131)

Les checkpoints et intégrations sont identifiables par commits : base de tâche, commit entrant, commit courant et commit intégré. Un conflit enregistre les IDs de tâche et de tentative, les trois commits, les fichiers et la sortie de fusion. L’intégration n’a pas de dates de début/fin dans son modèle. [Modèle de conflit](../../slopify/src/taskBatch.ts#L64-L85) · [Fusion, conflit et reçu d’intégration](../../slopify/src/taskBatch.ts#L435-L489)

Un signal d’activité minute est construit depuis les nouvelles lignes complètes de `stdout.log`, à défaut depuis le delta `git status --porcelain` du clone de tentative, sinon depuis une phrase « rien de nouveau ». Les signaux comportent runId, horodatage, tâche, phrase et source (`log`, `git`, `none`), puis sont conservés dans `activity.jsonl`. Ils ne comportent pas l’ID de tentative. Le signal est une observation d’activité, ni un pourcentage d’avancement ni une preuve que le processus est vivant : un agent silencieux peut être actif et des logs récents ne garantissent pas qu’il progresse. [Sources et composition du signal](../../slopify/src/taskBatch.ts#L328-L378) · [Contrat](../../slopify/src/activitySignal.ts#L6-L46) · [Persistance](../../slopify/src/activityJournal.ts#L10-L22) · [Décision ADR 0013](../adr/0013-emit-periodic-activity-signals.md#L15-L42)

## Disponibilité par mesure

| Mesure | Calcul exact disponible aujourd’hui | Proxy ou lacune | Instrumentation minimale pour une mesure durable |
|---|---|---|---|
| Comptes d’état | Comptage exact des `pending`, `running`, `completed`, `succeeded`, `failed`, `interrupted`, `blocked`, `conflicted` dans le dernier snapshot ; les listes « ready », « waiting » et « awaiting integration » sont aussi calculées. | L’historique des transitions n’est pas gardé dans `state.json`; le CLI fournit des mises à jour live mais pas une série durable de snapshots. | Journal append-only des transitions d’état, horodatées, en conservant le snapshot courant comme vue matérialisée. |
| Attente de dépendance | Dépendances non réussies d’une tâche `pending` ou `blocked`, et tâches immédiatement prêtes, sont calculables à l’instant du snapshot. | Aucun horodatage du moment où une tâche est devenue prête ou du début d’attente ; durée d’attente impossible à calculer précisément. | Événements `dependency-ready` et `attempt-started` avec horodatage, tâche et dépendances. |
| Durées tâche/tentative | Les tentatives et leurs états existent. `commands.jsonl` consigne un horodatage de début et de fin pour chaque sous-processus. | Pas de bornes sémantiques `taskStartedAt/taskFinishedAt` ou `attemptStartedAt/attemptFinishedAt`. L’intervalle des commandes est un proxy : il inclut préparation et opérations auxiliaires, et ne couvre pas les transitions de sauvegarde. `updatedAt` est un horodatage global fréquemment réécrit, pas une durée d’exécution ; reprises et attentes de résolution peuvent l’allonger. | Émettre les instants de lancement et de fin d’exécution d’agent par tentative, puis les instants d’intégration séparément, avec temps monotone pour calculer les durées et date UTC pour affichage. |
| Reprises / retries | Nombre et issue des tentatives sont exacts dans le tableau `attempts`; le nombre de reprises est dérivable comme `max(0, attempts.length - 1)`. | Pas de champ structuré « raison de la reprise » ; le rapport de tâche met surtout en avant la dernière tentative. | Événement de reprise avec tentative précédente, déclencheur (échec/interruption/action explicite) et nouvelle tentative. |
| Intégration | État intégré, commits avant/après, commit intégré et diagnostic d’échec sont présents. `completed` distingue l’attente d’intégration de `succeeded`. | Pas de durées d’intégration ; le conflit n’a pas d’horodatage dédié. Une résolution manuelle a `createdAt` et `validatedAt`, mais pas une durée de traitement automatiquement imputable. | Événements `integration-started`, `integration-succeeded`/`integration-failed`, `conflict-opened` et `resolution-validated`, tous liés au run, à la tâche et à la tentative. |
| Concurrence / vagues | La limite est exactement dix tâches par vague. L’état courant permet de compter les tâches `running`. L’ordre de sélection et d’intégration est déterministe par ordre JSON. | Aucun `waveId`, début/fin de vague ou pic de concurrence n’est conservé dans le snapshot final ; le calcul d’un pic historique à partir des instantanés exige que le client ait enregistré les callbacks live. | Enregistrer l’ID de vague, ses tâches sélectionnées, début/fin, et les événements de tentative. Le pic devient alors le maximum des tentatives qui se chevauchent. |
| Descendants bloqués | Les tâches bloquées et leurs dépendances responsables immédiates sont exactes dans `blockedBy`; le scheduler propage le blocage aux descendants. | Pas de `blockedAt`, de durée, ni de cause racine dénormalisée. | Événement `task-blocked` horodaté, avec bloqueurs directs et tâche(s) racine(s) en échec. |
| Échecs / conflits | États de tâche/tentative, codes de diagnostic, sorties, code de sortie, fichiers en conflit et commits concernés sont conservés. Le rapport qualifie les diagnostics et expose les problèmes courants. | Les diagnostics structurés ne sont pas une taxonomie uniforme de cause ; le rapport de tâche consulte les diagnostics de la dernière tentative, alors que le snapshot garde les précédentes. | Conserver un événement de résultat par tentative et des catégories stables de résultat (échec agent, exécution, intégration, interruption, nettoyage) ; journaliser ouverture, résolution et issue du conflit. |
| Activité | Les signaux et leur horodatage/source sont persistés ; jusqu’aux dix plus récents sont affichés par `tasks status`. | Ce texte mécanique indique qu’un log ou un fichier a changé, ou qu’aucune nouvelle n’a été observée. Il ne constitue ni une progression quantifiée, ni un contrôle de santé du processus. Le schéma omet `attemptId`. | Ajouter `attemptId` aux signaux pour l’attribution. Si une mesure de progression est voulue, définir et journaliser des événements de jalon explicites séparément des signaux d’activité. |
| Tokens / coût | Les tâches portent agent, modèle éventuel et effort ; les logs et rollouts Codex sont conservés comme éléments de preuve. | Aucun champ normalisé de tokens, coût, fournisseur ou version effective du modèle dans `TaskExecutionResult`, `BatchTaskAttempt` ou le rapport. Les traces brutes éventuelles ne donnent pas à elles seules une mesure comparable inter-agents. | Extraire les compteurs d’usage du fournisseur dans un contrat `usage` par tentative (tokens entrée/sortie/cache, devise, coût, fournisseur et modèle effectif) ; distinguer « indisponible » de zéro. |
| Comparaison inter-runs | Chaque run a un UUID, dépôt, base Git et copies figées du batch et de la spec ; son `state.json`/journal d’activité est stocké séparément. | Le service expose le statut pour un run connu, sans index/liste de runs. Pas de hash explicite des entrées ni de version d’exécuteur/modèle pour établir la comparabilité ; pas d’usage normalisé. | Index léger des runs avec hash de spec/batch, commit de code, agent/modèle/version effectifs et schéma de métriques ; conserver les événements par run pour agréger des cohortes comparables. |

Sources des événements de sous-processus (`commands.jsonl`) et des traces : [DockerTaskExecutor](../../slopify/src/dockerTaskExecutor.ts#L40-L60). Le contrat de résultat contient code de sortie, checkpoint, chemins de sortie, ressource et diagnostics, sans dates ni usage normalisé : [TaskExecutionResult](../../slopify/src/taskExecution.ts#L11-L45). L’aide CLI confirme les dix tâches prêtes, les canaux de progression/signal et la prudence sur `running` : [taskBatchCli.ts](../../slopify/src/taskBatchCli.ts#L30-L49).

## Séparer données et choix de produit

Les tableaux ci-dessus recensent les faits calculables et les champs manquants ; ils ne choisissent ni visualisation, ni métrique produit, ni stockage final. Le socle le plus petit pour calculer dans le temps les durées, attentes, vagues et résultats est un journal de transitions horodatées portant `runId`, `taskId`, `attemptId` et, pour le scheduler, `waveId`. Les signaux d’activité doivent rester identifiés comme observations distinctes des transitions et des résultats.
